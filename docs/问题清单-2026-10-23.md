## 1. 已复现的缺陷（附复现结果）

| 编号 | 严重度 | 位置 | 现象 | 复现结果 |
|---|---|---|---|---|
| D1 | **P0** | `core.py:953` `unique_path()` + `webui.py:261` | **并发任务会拿到同一个文件路径**，互相覆盖 | 两个线程同时调 `unique_path(dir,'同名','mp4')`，返回完全相同的路径（因为路径没被占位，只是查了一下不存在） |
| D2 | **P1** | `webui.py:478` → `core.py:111` | `/api/parse` 收到非字符串 `text` 直接崩掉，连接被重置，前端只看到「连不上本地服务」 | `{"text":123}` / `{"text":[...]}` / `{"text":true}` 三种都是 `RemoteDisconnected`；只有正常字符串返回 200 |
| D3 | **P1** | `core.py:962` `download_gallery()` | **图集部分图片失败时静默出一个残缺 zip**，用户以为完整 | 三张图里第二张 404 → 正常返回 `测试图集.zip`，里面只有 1 张，无任何警告 |
| D4 | **P2** | `core.py:919` `download_stream()` + `webui.py:261` | D1 的连带伤害：下载失败时 `except BaseException: os.remove(path)` 会删掉**另一个任务**正在写的同名文件 | 代码路径确定，随 D1 一起触发 |

### D1 详情：并发同名任务会撞同一路径

`unique_path()` 只做「存在就 +1」的判断，不创建占位文件：

```python
def unique_path(folder, base, ext):
    path = os.path.join(folder, "%s.%s" % (base, ext))
    n = 1
    while os.path.exists(path):      # 判断完到真正创建之间没有任何保护
        ...
```

而网页版的下载是**每个任务一个线程、并发跑**（`webui.py:261`）。触发场景很常见：

- 同一条链接粘两次 → 两个任务的 `base` 完全相同；
- 主页批量里作者自己转过同一个作品；
- 「两个都要」以外的重复提交。

后果：两个线程写同一个 mp4，文件交错损坏；其中一个失败时 `download_stream` 还会把文件删掉。**README 里写的「同名文件不会覆盖，会自动加 (1)、(2)」在并发下不成立。**

> 建议方向（本次不实施）：用 `open(path,'xb')` 原子占位，或先写 `xxx.mp4.part` 再 `os.replace()`；`download_stream` 失败时只删自己创建的那个 `.part`。

### D2 详情：`/api/parse` 对畸形 `text` 没有兜底

PR #10 已经给 `versions`、`_read_json`、`save_meta` 都加了类型兜底，唯独漏了最外层的 `text`：

```python
urls = core.extract_urls(data.get("text") or "")   # webui.py:478
```

`extract_urls` 内部直接 `URL_RE.finditer(text)`，非字符串就抛 `TypeError`，handler 没有 try，客户端拿到的是**连接被重置**而不是一条 JSON 错误。这与 README「拒绝畸形输入」的承诺不一致，也说明这类入口还可以继续收紧（`quality`、`prefer_h264` 同样没有类型校验，传 `"false"` 字符串会被 `bool()` 成 `True`）。

### D3 详情：图集静默丢图

```python
try:
    download_stream(u, target, timeout=45)
    files.append(target)
except Exception:
    continue          # core.py:975 —— 哪张失败、失败几张，全都不告诉用户
```

`if not files:` 只挡住「一张都没成功」。3 张里成功 1 张，依然打包成 zip 并返回成功。图集这类内容丢一张往往就是丢主体图，建议至少把失败张数回传给界面/命令行。

## 2. 健壮性缺口（代码审查，未在真实抖音环境验证）

| 编号 | 位置 | 问题 | 影响 |
|---|---|---|---|
| R1 | `webui.py:39` `_thumbs` | 缩略图缓存在内存里，**没有上限、也没有过期**，单张最多 2 MB | 长时间挂着网页版下几百个作品，内存只增不减，最终可能被系统杀掉 |
| R2 | `webui.py:33-34` | `_jobs` / `_job_order` 只在「删任务」时才清理 | 同上，长跑必然膨胀 |
| R3 | `webui.py:261` | 每个任务开一个线程下载，**没有并发上限** | 主页一次抓 20 个 = 20 个并发连接同时拉；带宽被打满、更容易被风控，文件句柄也吃紧 |
| R4 | `core.py:1094` `extract_mp3()` | `subprocess.run(...)` **没有 `timeout`** | ffmpeg 卡住（坏文件、路径异常）时该下载线程永久挂死，界面上任务永远停在「下载中」 |
| R5 | `core.py:919` `download_stream()` | 没有重试、没有断点续传 | 网络抖动一次整个任务失败，已下的部分全丢（还会删文件） |
| R6 | `core.py:928` | 直接写最终文件名，不用 `.part` + 原子改名 | 进程被强杀/断电时留下一个**看起来正常、其实放不了**的半截 mp4（异常路径会删，`SIGKILL` 不会） |
| R7 | `core.py:928` | 不校验 `Content-Type` / 文件头 | CDN 返回 200 的 HTML 错误页会被当成 `.mp4` 存下来 |
| R8 | `core.py:217` `_WS.recv()` | 不处理 WebSocket **分片帧**（continuation `opcode 0x0`，被当作 ping 丢弃）；握手也不校验 `Sec-WebSocket-Accept` | 响应体较大被 Chrome 分片时，`json.loads` 拿到半个包会失败；属于「平时不出事、出事很难查」的那类 |
| R9 | `core.py:718` `_collect_links()` | 靠「连续 4 次没有新链接」判断加载结束，首次加载慢/需要登录时会提前收工 | 主页只抓到一部分（README 已有这条 FAQ，但代码里没有滚动重试或「加载中」判断） |
| R10 | `core.py:888` | 图集图片地址只用 `url_list`，绕过了 `spec.py` 的候选表 | 与「抖音改版只改 spec.py」的约定不一致，图集接口改名时这里要单独改 |
| R11 | `core.py:578` `_apply_stealth()` | 固定用 `msg id = 4/5`，与 `_capture()` 里的 `1/2/3/4` 重号 | CDP 响应靠 id 匹配，重号让抓包调试时很难判断哪条响应属于谁 |
| R12 | `core.py:424` `self._cache` | 作品详情缓存无上限 | 主页抓 200 个作品约几百 MB 常驻内存 |
| R13 | `webui.py:511` | `/api/retry` 对不存在的 id 也照样入队（实测返回 200） | 队列里堆垃圾项，排查问题时误导 |

另外两处安全边界（属设计取舍，不算 bug，但值得写进 README）：

- **本地服务没有令牌**，只靠 `Host` + `Origin` 拦浏览器跨站。同机任意进程都能 `POST /api/remove` 删掉下载目录里的文件，也能 `GET /api/file` 把文件读走。对本机小工具可以接受，但「能挡 DNS rebinding」不等于「有访问控制」。
- **配置目录不可写时没有降级**：程序装在 `C:\Program Files\...` 这类只读位置时，`os.makedirs(folder)` 和首次写 `config.json` 会直接抛异常退出，而不是退到用户目录。

## 4. 需要作者决策 / 我无法独立解决的问题

这几项不是改几行代码能收尾的，需要维护者拍板，也是本次想通过 PR 抛给作者的部分：

1. **抖音接口改版与风控对抗无法离线验证。** `spec.py` 的候选字段表、UA 伪装、`aweme/detail` 抓包路径，只有对着真实抖音跑才有意义。需要一个长期稳定不删的公开样片 + 在 CI 里加每日 `schedule` 跑 `--selftest`，否则「改版了」永远是用户报上来才知道。
2. **macOS / Linux 只验证过单测，没验证过真实下载链路。** CI 的三个平台只跑不联网的单测；`open_in_file_manager`、`ps` 清理进程、浏览器路径发现这些只在代码层面做过兼容，README 也承认「没有充分验证」。这需要真机（或 CI 上的浏览器）跑一遍。
3. **合规与公开风险。** 工具靠无头浏览器绕过 `a_bogus` / `msToken` 签名拿无水印流，与平台条款存在冲突；仓库是 public，被投诉下架的风险是真实的（这一点在 10-22 的对话里已经讨论过）。是否继续公开、README 的免责声明要写到什么程度，需要作者决定。
4. **图集「带水印」的口径不统一。** 命令行选「两个都要」时，图集静默只产出一个 zip、不讲原因；网页版会明确标「图集没有带水印版本，已跳过」。两个入口行为应当一致，但说不说、怎么说，是产品口径问题。
5. **带水印只有 720P 是平台限制**，不是 bug。是否要在界面上直接写出来（现在只在 README 的 FAQ 里），需要作者定。

## 5. 另一个必须先说的状态问题：工作区有一份没提交的重构，会让现有测试变红

工作区里有**不是我做的**未提交改动（`app.py` +133、`core.py` +98/-29，新增未跟踪的 `spec.py`）。按 HEAD 干净检出跑测试是 **138/138 全绿**；按**当前工作区**跑是 **136 通过 / 2 失败**：

```
FAIL: test_all_good_returns_zero (test_app.CheckEnvTests)   AssertionError: None != 0
FAIL: test_missing_browser_returns_one (test_app.CheckEnvTests)  AssertionError: None != 1
```

根因很清楚：`check_env()` 现在的写法**没有 `return`**（返回 `None`），而原本那行 `return 1 if issues else 0` 被挪到了 `self_test()` 的末尾，紧跟在 `return 0` 之后 —— 成了**永远执行不到的死代码**，`--checkenv` 因此永远返回 0，缺依赖时脚本也判断不出来。

一旦把这份改动推上去，CI 立刻变红。建议合并前先修这两行，并补一条 `--checkenv` 退出码的用例（现有用例本来就能抓到，是这份改动把它弄红的）。
